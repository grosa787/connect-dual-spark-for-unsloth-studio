## Проверка Spark Link 1.2.0 (31.10.2026)

- Пройдены 138 тестов CLI. В наборе приложения 42 проверки: 40 прошли в Qt runtime, две зависящие от PyYAML отдельно прошли в системном Python Ubuntu (пять сетевых проверок в этом запуске).
- Реальный Qt ARM64: шесть вкладок, четыре языка, ракурсы и всплывающий список, вертикальные/смешанные корпуса, черновики портов, сцена будущего третьего устройства и окно 1000×700.
- Воспроизведено исчезновение корпусов после скрытия окна. Сохранение узлов сцены при разрешённом освобождении контекста и кэшей проходит визуальную проверку; ручная перезагрузка сеток отклонена после сбоя Qt в отладчике.
- Установлен `.run` 1.2.0: независимый Qt, скрытый запуск, открытие через IPC с видимыми корпусами, повторное скрытие, Studio HTTP 200 и доступный RPC. Пример RSS: 399,2 / 404,9 / 401,0 МиБ, больше прежней упрощённой сцены.

# Проверка Spark Link 1.1.1

Проверено 31 октября 2026 года на имеющейся паре DGX Spark с Ubuntu 24.04 ARM64.

В [отчёте о скорости и вместимости](../docs/startup-and-mistral-2026-10-31.ru.md) и [JSON проверки](../docs/startup-mistral-validation-2026-10-31.json) зафиксирована версия 1.1.1: **138 тестов CLI и 41 тест приложения**, безопасная асинхронная RPC-загрузка, реальные текст/vision на Q8, сравнение Mistral при минимальном контексте и полная обработка промпта из 106240 токенов. Две проверки netplan отдельно выполнены системным Python Ubuntu. После установки 1.1.1 снова прошли нативные проверки шести вкладок на четырёх языках и запуск через пункт меню. Остальные пункты ниже сохраняют прежние проверки как историю покрытия.

В последующем [отчёте об обновлении среды](../docs/runtime-update-2026-10-31.ru.md) зафиксированы успешная пересборка Unsloth 2026.10.11 / llama.cpp b11985, реальные запросы к Q8 через Studio с текстом и картинкой при настроенном контексте 1048576, буферы весов/KV на каждом устройстве и выгрузка модели после тестов. Там же описан настоящий откат после неудачной загрузки, дополняющий изолированные сценарии ниже.

- Тесты CLI: **132 прошли**.
- Тесты управления приложением: **40 проверок**. В изолированном Qt runtime прошли 38, ещё две проверки netplan/PyYAML отдельно прошли в системном Python Ubuntu. Проверены откат неработающего обновления, восстановление JSON, метаданные моделей без интернета, обнаружение кабелей без дублирования логических линий, отдельные манифесты workers, распределение памяти и контекста, удаление правил конкретной модели и безопасная передача пароля через stdin.
- Настоящий Qt Quick / Qt Quick 3D интерфейс: шесть вкладок на четырёх языках, данные двух реальных Spark, вертикальное и смешанное положение корпусов с сохранением, состояние ещё не подключённого третьего устройства, выбор порта клавиатурой, сохранение черновика при обновлении данных, проверка несовпадающей схемы, освобождение графических ресурсов при скрытии. Скриншоты сделаны при 1240×820 и 1000×700. Ошибок загрузки и типов QML нет.
- Реальные метаданные Hugging Face и интерфейс планировщика: ограниченное чтение заголовка Qwen3-0.6B GGUF, заявленный контекст 40960, варианты модели, оценка кеша, автоматические и ручные проценты/GiB, заполненные формы на четырёх языках и четыре варианта диалога с замаскированным паролем. Тест не отправляет реальные учётные данные и не добавляет устройство.
- Изолированный GNOME Keyring: тестовые пароль и параметры подключения записаны, прочитаны и удалены; в файлах хранилища открытый тестовый пароль не обнаружен. Настоящие пароли пользователя тест не читает.
- Реальная генерация на двух устройствах: небольшая кешированная Qwen GGUF, сохранённое распределение 45:55 и контекст 512 вместо устаревшего аргумента 8192, непустой ответ модели и одновременно HTTP 200 от Studio. Завершён только тестовый процесс модели, затем удалён его план. Пользовательские модели не загружались и не выгружались.
- Фоновая проверка восстановления: установленная версия исходников и сборки совпадает, fastload не переключался, Studio/RPC доступны без загрузки ПО. На первом Spark подтверждён `Linger=yes`.
- Фоновый запуск установленного приложения: скрытый старт, открытие существующего окна через IPC, повторное скрытие, доступность Studio/RPC. В тестовом сеансе Spark/Xvfb RSS составил примерно 347 МиБ при старте, 351 МиБ с окном и 286 МиБ после скрытия и освобождения графики. Это измерение, а не гарантированный предел потребления памяти.
- Существующая сеть: применение уже действующей схемы порта 0 без изменений, проверка прямых маршрутов и ping в обе стороны; SSH и сборки host/worker согласованы. Административное изменение netplan не потребовалось: адреса уже соответствовали схеме.
- Самораспаковывающийся релиз установлен на первый Spark с собственным Qt runtime. Импорты `spark_link` и `dual_spark` идут из приложения, а не из установленной CLI.
- Опубликованный GitHub-установщик выполнен с отдельно переданным tar.gz через `--archive`: распаковка и установка встроенных wheels без скачивания Python-пакетов прошли. Контрольные суммы файлов GitHub совпадают с SHA256SUMS. Полная загрузка началась, но была остановлена из-за скорости около 60 КБ/с на этом Spark; идентичный архив передан для проверки по локальной сети.
- Созданный `.desktop` прошёл `desktop-file-validate` и запущен через `gio launch` в Xvfb: появилось нативное окно. Ярлык рабочего стола имеет `metadata::trusted=true`.
- Независимый шлюз распределения памяти на стандартной библиотеке Python вызывает сохранённый пользовательский launcher Q8 43:57 с SHA-256 `cddb6aec3304021e2a759cca302ed952c95b809eb422b59f6e4561859e4da59e`. Генерация не требует runtime графического приложения. Studio/RPC продолжают работать.

## Практические ограничения

Административная смена портов покрыта проверками входных данных и отката, но физическая перестановка кабеля при проверке этого релиза не выполнялась. Для смены порта нужно переставить кабель и пройти sudo-авторизацию на затронутых устройствах.

Топология трёх устройств и построение команд проверены программно. Трёх физических Spark пока нет. Генерацию с двумя workers, первую настройку третьего Spark и маршруты трёх устройств нужно проверить после его подключения. В интерфейсе и документации этот режим отмечен экспериментальным. Переноса уже работающей модели при отключении устройства нет.

Отрисовка и запуск через меню проверялись в виртуальном X11-дисплее: первый Spark находился на экране графического входа. Приложение установлено в меню и на рабочем столе пользователя для обычного графического сеанса.

Физическое отключение питания, интернета и первый вход по паролю на неизвестный третий Spark не проверялись на оборудовании. Восстановление и откат проверены изолированными сценариями прерванного обновления; проверка на реальной паре не требовала изменений. Генерация не может продолжаться при потере необходимого worker. Для фонового административного восстановления нужно защищённое и разблокированное хранилище GNOME; обычный запуск системной службы RPC не требует открытого GUI или сохранённого пароля.
